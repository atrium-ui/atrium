# Atrium UI Kits

Reusable, ready-to-use UI kits. Unlike single components, a kit is a **whole set of
styled UI components** (buttons, tabs, inputs, dialogs, lists, tables, ...) that
share one theme (primary / accent colors + Tailwind styles).

Key properties:

- **Framework-agnostic.** Kit files are plain `.html` snippets. No React / Vue / Solid
  required. Behavior comes from our headless custom elements (`@atrium-ui/elements`,
  plus `@atrium-ui/panels` for tabbed panels),
  icons from a pre-built inline SVG sprite (no icon runtime), styling from global
  Tailwind classes + one `theme.css`.
- **Copy-paste.** Copy the kit folder into any project, or download the zip from the docs.
- **Previewed with a framework.** In the docs we render the same HTML inside Astro so
  you see live examples.

Every kit is a contract: same 19 components, same theme tokens, same
framework-agnostic HTML. This guide defines what each block is and what "done"
looks like, so kits stay interchangeable. For a live reference, see the
[Basics kit](https://atrium-ui.dev/kits/basics) in the docs.

## Layout

```
packages/kits/
  src/
    <kit>/               e.g. `basics/`
      kit.json           manifest (name, slug, version, sections, showcase)
      theme.css          Tailwind v4 `@theme` tokens: primary + accent colors
      index.html         generic dashboard composing all components (copy-paste starter)
      README.md          per-kit usage (deps, install, theming)
      sections/
        *.html           one file per outline item, pure HTML + elements
      icons/
        *.svg            raw icon set (owned copy; sprite it or inline per snippet)
  dist/                  generated `<kit>.zip` files (gitignored, built via `bun run build`)
                          — each zip includes a compiled `global.css` (base +
                          used utilities + theme tokens, via the Tailwind CLI)
  build.ts               zips each kit (+ compiles global.css) and copies
                          zips + .css files to `docs/assets/kits/`
```

## Using a kit (zip only, v1)

1. Download the zip from the docs (`/kits/<kit>.zip`).
2. Unzip into your project, e.g. `src/ui-kit/`.
3. Install runtime deps:

   ```bash
   bun add @atrium-ui/elements @atrium-ui/panels
   # tailwindcss v4 required for the utility classes
   ```

4. Import the theme once in your Tailwind v4 stylesheet (e.g. `src/index.css`).
   Do not `<link>` it in HTML — `@theme` tokens only register when compiled:

   ```css
   @import "tailwindcss";
   @import "./ui-kit/theme.css";
   ```

   Then import the elements once (e.g. in your global layout / entry):

   ```html
   <script type="module">
     import "@atrium-ui/elements";
     import "@atrium-ui/panels"; // tabbed panels (only needed if you use the tabs section)
   </script>
   ```

   Icons need no import: paste the zip's `icons/sprite.html` once near the top
   of `<body>` and reference symbols natively.

   ```html
   <svg class="h-4 w-4" aria-hidden="true"><use href="#kit-icon-search"></use></svg>
   ```

5. Copy any `sections/*.html` snippet into your pages. They are plain HTML —
   adapt classes and tokens to your brand.

No Tailwind build step? Skip steps 3–4's Tailwind wiring and `<link>` the
zip's pre-compiled `global.css` instead — one minified stylesheet with base
reset, the utilities the kit's HTML uses, and its theme tokens baked in. Regenerated by
`bun run build` (see Layout above) via the Tailwind CLI.

## Authoring rules for kit sections

- Pure HTML only. No framework syntax (`v-`, `:prop`, `{expr}`, JSX).
- Only dependencies besides Tailwind are `@atrium-ui/elements` custom elements
  (`a-tabs-*`, `a-toggle`, `a-range`, `a-select` / `a-option`, `a-color-picker`,
  `a-expandable`, `a-list*`, `a-track` for carousels, `a-portal` + `a-blur` for
  dialogs, `a-popover-*` + `a-tooltip` for popovers) and `@atrium-ui/panels`
  (`a-panel` for tabbed, dockable panels).
  Icons are plain `<symbol>` defs referenced with `<use>` — never an icon component.
- All brand color goes through `theme.css` tokens (`--color-primary-*`,
  `--color-accent-*`). Sections must not hardcode hex brand colors.
- Every section file must be renderable standalone in the docs preview.
- Each section file starts with a `<!-- requires: ... -->` comment listing the
  element import it needs, followed by a
  `<!-- Built with Atrium UI — https://atrium-ui.dev/ -->` back-reference
  comment. Keep the back-reference when copying or adding sections.

## The 19 components (outline of contents — every kit must cover all of them)

### Tabs

Tabbed navigation over stacked panels — tabs and panels are one block, and each
kit defines how tabs function. The basics kit uses the standard `a-tabs`
elements (`a-tabs-list` / `a-tabs-tab` / `a-tabs-panel`): exactly one tab
selected, arrow keys / Home / End move between tabs, inactive panels hide via
`hidden="until-found"`. The workbench kit uses the dockable `a-panel` groups
from `@atrium-ui/panels` instead: each child carries a `tab` label, the
`active-tab` attribute picks the visible view, and tabs can be dragged to
dock or split. Use tabs when several views share one region; don't use them
for sequential steps (that's a wizard).

### Buttons

The action vocabulary: primary, outline, ghost, disabled, plus an accent link.
Primary is reserved for the single most important action per surface; everything
else steps down a variant. Disabled uses `aria-disabled` styling (kept focusable),
never a bare `disabled` grey box without explanation.

### Colors

One section per kit: the primary brand ramp (`--color-primary-50` → `-950`) plus
the accent ramp. Primary carries actions, active states, and tinted surfaces
(`bg-primary-500`, `bg-primary-50/100`, `text-primary-700` on light). Accent is
reserved for highlights, badges, and active markers — never body text or primary
actions. If a section needs a brand color not on these ramps, the ramps are
wrong — fix `theme.css`, not the section.

### Numeric sliders

Single-value sliders built on `a-range`, always paired with an `<output>` showing
the number. The element is unstyled by design — the kit themes it via
`--theme-color` in `theme.css`. Use for volume, brightness, quantities; use a
text input when exact values matter more than dragging.

### Text inputs

Labelled text, email, textarea, and number fields with placeholders, focus rings
in primary, and consistent padding/borders. Optionally wires into
`a-form-field` for validation. Every input has a real `<label>` — placeholders
are hints, not labels.

### Select

Single-choice dropdowns built on `a-select` / `a-option`: a labelled trigger
button with chevron, a list of options, and form association via `name`.
Keyboard: arrows move highlight, Enter commits, Escape closes, typing jumps by
initial. Use for fixed enums (locale, plan, sort order, shading mode); keep
radios when every option must stay visible, and text inputs when the value is
free-form. The trigger label is kit-owned UI — sync it from the `change` event
(the element does not rewrite the slot).

### Color picker

`a-color-picker` with its 2D saturation/value field, hue slider, and hex input.
Kits show the basic picker plus the alpha + palette-preset variant. Used for
brand/theme customization surfaces.

### Detail expands

Collapsible disclosures built on `a-expandable` with a `slot="toggle"` button —
shipping details, return policies, FAQs. One item ships `opened` to demonstrate
the default-open state. The toggle always carries a visible affordance (chevron
or `+`), and content stays in the DOM when collapsed.

### Text definitions

Term–definition pairs (`dl` / `dt` / `dd`) for plans, seats, retention rules —
the "glossary row" pattern. Responsive two-column layout, `dfn` on the defined
term. Screen readers announce the pairing, which a table or bold-paragraph
approximation would lose.

### Tables

Data tables with `caption`, `th scope`, `tbody` rows, and `tfoot` totals.
Tabular numerals, row hover in `primary-50`, status pills. The caption and footer
are mandatory parts of the snippet — a table without a summary is unfinished UI.

### Dialogs

Interruptive tasks (confirm delete, edit record) via native `<dialog>` — focus
trap and Esc come free — with header / body / footer-button structure. The
snippet also documents the `a-portal` + `a-blur` variant for apps needing the
Atrium overlay behavior with identical kit styling.

### Lists

Single-column rows built on `a-list` / `a-list-item`: avatar, name + meta,
status pill. Hover surfaces in `primary-50`. Used for members, files, settings
rows — anything selectable or navigable in one dimension.

### Gallery

The two-dimensional sibling of lists: a grid of tiles (artwork, photos,
products) reusing `a-list` semantics with `aspect-square` media and text labels.
Tiles keep a visible border and hover elevation; media always has a text
alternative (`role="img"` + label, never bare decoration for meaningful images).
For overflowing rows that scroll horizontally, see carousel.

### Carousel

Horizontal snap scrolling built on `a-track`, like the carousel component:
a `snap` track of `flex-none` slides, prev/next buttons calling `moveBy(±1)`,
`scroll` / `change` events available for progress indicators. Use for
recently-modified rows, galleries, and onboarding; never autoplay content
users must read, and always keep every slide reachable by keyboard
(the track is focusable, buttons are real buttons).

### Teaser

A single content card: muted tile with a glyph, small date, serif italic
title. Used for recently-modified docs, search results, and anywhere one item
must invite a click. Tile, date, and title form one link with a single
accessible name (`aria-label` on the link, `aria-hidden` on the decoration).
Galleries are grids of teasers; carousels are tracks of teasers.

### Checkbox

Multi-select choices built on `a-toggle` as checkable cards. The checked state
styles via `has-checked:` on the label and a check svg in the `true` slot.
Grouped in a `fieldset` with a `legend` — a set of checkboxes is one question,
not N independent toggles.

### Switch

Binary on/off settings built on `a-toggle` as sliding switches in labelled rows.
The knob slides via `true`/`false` slots (`ml-auto` when on). One switch, one
immediate effect — anything needing Apply/Confirm is a checkbox or button, not
a switch.

### Icons

An inline sprite of `<symbol>` defs (`kit-icon-*` prefixed ids to avoid
collisions), referenced with `<svg><use href="#kit-icon-name"></use></svg>` —
native, zero JS. Icons size with `text-*` (1em box) and inherit `currentColor`.
Decorative icons are `aria-hidden`; meaning never rides on icon alone. The raw
set lives in `icons/*.svg`; `bun run build` compiles it into the pasteable
`icons/sprite.html` shipped in the zip, normalizing hardcoded fills to
`currentColor`. External `<use href="sprite.svg#id">` is not used — WebKit does
not resolve cross-document references.

### Popover / context menus

Floating UI on `a-popover-trigger`: click menus (`a-popover` with
`role="menu"` / `menuitem`, separators, `kbd` hints), hover/focus tooltips
(`a-tooltip`, which also opens on right-click), and context-style row menus.
Panels animate off the `enabled` attribute the element sets when open. Escape
always dismisses; triggers expose `aria-haspopup` / `aria-expanded`.

## Definition of done

- [ ] All 19 snippets exist in `sections/` and are listed in `kit.json`.
- [ ] `index.html` previews every section; `icons/` holds the raw set.
- [ ] No hardcoded brand hex; `theme.css` is the only color source.
- [ ] Each snippet names its `requires` imports; the kit installs with
  `@atrium-ui/elements` (+ `@atrium-ui/panels` for the tabs section) and Tailwind v4 — no icon runtime.
- [ ] `bun run build` in `packages/kits` produces the zip served from the docs.
